# 工具清单

> 本文是整个项目最重要的一张表。它决定了 Agent 的能力边界、权限模型、审批范围与评测口径，
> 一旦改动，提示词、权限码、审计表、评测集都要跟着改。所以先在这里定死，写代码时只做微调。

## 一、列定义

| 列名 | 说明 |
|---|---|
| 工具编码 | 全小写下划线。Agent 调用时用的名字，**代码、提示词、数据库里必须完全一致** |
| 中文名 | 给人看的 |
| 描述（给模型） | 直接进 OpenAI `tools[].function.description`，**必须写清"什么时候用"** |
| 参数 | 格式 `名字:类型,必填?`，例如 `ticketId:long,必填` |
| 读/写 | `读` / `写` |
| 需审批 | 写操作一律 `是` |
| 权限码 | 两段式 `模块:操作` |
| 幂等 | `是` / `否`。写操作必须 `是` |
| 超时 ms | 默认 5000，外部系统 3000 |
| 重试次数 | 读操作 2，写操作 0 |
| 落哪张审计表 | 默认 `sys_audit_log` |

## 三、B 类：内部写工具（5 个，全部需审批）

| 工具编码 | 中文名 | 描述（给模型） | 参数 | 权限码 | 幂等键 |
|---|---|---|---|---|---|
| `ticket_create` | 创建工单 | 创建一个新工单。当用户描述了问题、且需要把它登记成一个工单跟进时调用。**这是写操作，执行前必须先向用户复述标题、分类、优先级并获得明确同意。** | title:string,必填 / content:string,必填 / categoryId:long,必填 / priority:string,必填 / requesterId:long,否 | `ticket:add` | `runId:step:code:hash(args)` |
| `ticket_assign` | 指派或转派工单 | 把工单指派给某个客服，或从当前处理人转派给他人。当用户说"转给谁""指派给谁"时调用。**写操作，需先确认。** | ticketId:long,必填 / assigneeId:long,必填 / reason:string,否 | `ticket:assign` | 同上 |
| `ticket_update_status` | 流转工单状态 | 把工单从当前状态流转到目标状态。只能走系统允许的状态白名单。当用户说"标记为已解决""关掉这个工单"时调用。**写操作，需先确认；关闭类操作要提醒不可恢复。** | ticketId:long,必填 / targetStatus:string,必填 / reason:string,否 | `ticket:update` | 同上 |
| `ticket_reply` | 添加工单回复 | 在工单下添加一条回复，可选择公开（用户可见）或内部备注（仅内部可见）。当用户说"回复他""记一条内部备注"时调用。**写操作，需先确认；内部备注要说明用户看不到。** | ticketId:long,必填 / content:string,必填 / visible:string,必填（public/internal） | `ticket:reply` | 同上 |
| `ticket_escalate` | 升级工单优先级 | 提高工单的优先级，通常用于紧急情况或 SLA 即将超期。当用户说"这个很急""升级一下"时调用。**写操作，需先确认。** | ticketId:long,必填 / targetPriority:string,必填 / reason:string,必填 | `ticket:update` | 同上 |

写工具共性：`read_only=0`、`need_approval=1`、`idempotent=1`、`max_retry=0`、`timeout_ms=5000`。

幂等键的构成：`runId`（本次运行）+ `step`（图上的节点序号）+ `工具编码` + `参数的稳定哈希`。
同一个键重复执行时直接返回上一次的结果，不真正落库 —— 这是"审批通过后进程重启、节点重放"时不产生重复工单的保证。

## 四、C 类：外部系统只读工具（2 个，跨系统）

| 工具编码 | 中文名 | 描述（给模型） | 参数 | 后端指向 |
|---|---|---|---|---|
| `external_dish_query` | 查外卖系统菜品 | 查询另一个外卖业务系统里的菜品信息（名称、分类、价格、状态）。当用户问到外卖菜品相关问题时调用。 | name:string,否 / categoryName:string,否 | 项目一 `GET /admin/dish/page` |
| `external_order_query` | 查外卖系统订单 | 查询另一个外卖业务系统里的订单信息（订单号、金额、状态、时间）。当用户问到外卖订单相关问题时调用。 | number:string,否 / phone:string,否 / status:string,否 | 项目一 `GET /admin/order/page` |

外部工具共性：`external_system='sky-take-out'`、`timeout_ms=3000`、`max_retry=1`、`need_approval=0`。
外部调用失败一律**降级为"暂时查不到"**，并把失败原因写进审计日志，绝不让异常穿透到对话里。

## 五、为什么这么设计

1. **写操作全部要审批** —— 模型不听话时，提示词是管不住的，只有代码强制才可靠。审批闸门放在工具执行器里，不在提示词里。
2. **外部工具统一 `external_` 前缀** —— 让模型和人都能一眼区分内外部能力，也方便按前缀做权限与限流。
3. **`faq_search` 与 `kb_search` 分开** —— FAQ 是精确问答对，比语义检索更快更准。分开之后模型才有明确的优先顺序，而不是在两者之间乱选。
4. **每个工具都写"什么时候用"** —— 只写"是什么"会导致模型该调不调、不该调乱调。描述里的触发条件就是提示词的一部分。

## 六、和别处的关系

| 落点 | 内容 |
|---|---|
| 数据库 `agent_tool` | 15 行，`code` 与本文完全一致 |
| 数据库 `agent.tool_scope` | 每个 Agent 能用的工具子集，售后 13 个、售前 4 个 |
| 权限表 `sys_permission` | 13 个权限码，工具的 `required_permission` 必须能在里面找到 |
| 评测集 `eval_case.expected_tools` | 只写本文出现过的编码，写错评测会一直判失败 |
| 审计表 `sys_audit_log` | 每次工具调用一行，含入参、出参、耗时、是否审批、是否幂等命中 |
