# 工单状态机

> 状态机是这个项目里最容易被做糊的地方。大多数同类项目把状态判断写成散落各处的 `if`，
> 结果就是"谁都能改、改完对不上"。这里把它收敛成一张表，代码里只有一份白名单。

## 一、状态码

用整数，不用字符串 —— 字符串在拼写、大小写、前后空格上都可能出错，且数据库里排序不直观。

| 码 | 状态 | 是否终态 | 含义 |
|---|---|---|---|
| 1 | 待受理 | 否 | 已创建，还没人接 |
| 2 | 处理中 | 否 | 已指派，正在处理 |
| 3 | 已挂起 | 否 | 等外部条件（客户补充信息、等物流等） |
| 4 | 待用户确认 | 否 | 客服认为已处理完，等用户确认 |
| 5 | 已解决 | 否 | 用户已确认解决 |
| 6 | 已关闭 | **是** | 归档结束，只能重开 |

只有 `6 已关闭` 是终态，且它也不是死路 —— 可以重开回 `2 处理中`。

## 二、流转白名单

**这张表会 1:1 变成 Java 里的 `Map<Integer, Set<Integer>>`，除此之外没有任何地方允许改状态。**

| 当前 | 允许流转到 | 谁可以操作 |
|---|---|---|
| 1 待受理 | 2 处理中、6 已关闭 | 客服、主管、管理员 |
| 2 处理中 | 4 待用户确认、3 已挂起、6 已关闭 | 处理人、主管、管理员 |
| 3 已挂起 | 2 处理中 | 处理人、主管、管理员 |
| 4 待用户确认 | 5 已解决、2 处理中 | 提交人、主管、管理员 |
| 5 已解决 | 6 已关闭、2 处理中（重开） | 系统、主管、管理员 |
| 6 已关闭 | 2 处理中（重开） | 主管、管理员 |

不在表里的组合一律拒绝，返回统一错误 `当前状态不允许该流转`，并把尝试记录进审计日志。
比如"1 待受理 → 5 已解决"是禁止的 —— 没受理就解决，说明流程被跳过了。

## 三、三条硬约束

1. **每次流转必须留痕。** 在 `ticket_status_log` 写一行：操作人、原状态、新状态、原因、时间。
2. **`已关闭` 不参与任何自动流转。** 定时任务不得把它改走，只能人工重开。
3. **流转与写日志必须在同一个事务里。** 用 `@Transactional` 包住，不允许一个成功一个失败。

## 四、自动流转规则

由定时任务（每 10 分钟扫一次）负责，全部走上面同一套白名单，不搞旁路。

| 条件 | 动作 |
|---|---|
| 「待用户确认」超过 3 天未响应 | 自动转「已解决」 |
| 「已解决」超过 7 天 | 自动转「已关闭」 |
| 超期未响应的「待受理」 | 触发升级：提高优先级 + 告警，**不改状态** |

最后一条特别说明：超期不改状态，是因为"没人接"和"已被关掉"是两回事。
把它改掉会掩盖问题，只提优先级加告警，让主管在列表里第一眼看到。

## 五、和别处的关系

| 落点 | 内容 |
|---|---|
| `ticket.status` | 存整数码，与本文一致 |
| `ticket_status_log` | 每次流转一行，是回放流程的唯一依据 |
| `ticket_escalate` 工具 | 只改优先级，不碰状态 |
| `ticket_update_status` 工具 | 唯一能改状态的入口，执行前需人工审批 |
| Agent 状态图的 `escalate` 节点 | 转人工时创建或指派工单，不直接改状态 |
| 评测 D 类用例 | 期望走转人工，而不是自己硬改状态 |
