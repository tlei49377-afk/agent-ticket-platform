# 评测指标

> 没有评测的 Agent 项目，简历上只能写"实现了智能客服"；
> 有评测的，可以写"工具命中率 88%，文档召回率 79%，平均 3.2 轮，单次成本 0.004 元"。
> 后者才是能被追问、也经得起追问的说法。

## 一、8 个指标

| # | 指标 | 计算方式 | 数据来源 | 第一版目标 |
|---|---|---|---|---|
| 1 | 工具命中率 | 实际调用工具集 ⊇ 期望工具集的用例数 / 总用例数 | `eval_result.actual_tools` vs `eval_case.expected_tools` | ≥ 85% |
| 2 | 关键词命中率 | 答案包含全部期望关键词的用例数 / 总用例数 | `eval_result.actual_answer` vs `expected_keywords` | ≥ 80% |
| 3 | 文档召回率 Recall@5 | 期望文档出现在检索 top5 的用例数 / 总用例数 | `kb_retrieval_log` vs `expected_doc_ids` | ≥ 75% |
| 4 | MRR | 期望文档排名倒数的均值 | 同上 | ≥ 0.60 |
| 5 | 忠实度 | LLM 裁判 1~5 分均值（陈述有据可查） | `eval_result.judge_score` | ≥ 4.0 |
| 6 | 相关性 | LLM 裁判 1~5 分均值（切题程度） | 同上 | ≥ 4.0 |
| 7 | 平均轮次 | Σ 模型调用次数 / 用例数 | `agent_message` | ≤ 4 |
| 8 | 平均成本 | Σ token 费用 / 用例数 | `agent_message.cost` | 只记录，先不设目标 |

几点说明：

- **指标 1 用"实际 ⊇ 期望"而不是"完全相等"** —— 模型多调一个合理的只读工具不该被判失败，
  但少调了必需的工具必须判失败。写操作则相反，见下面的审批触发率。
- **指标 3、4 依赖阶段 5** —— 知识库入库之前，`expected_doc_ids` 是空跑，先把管道搭好。
- **指标 8 不设目标** —— 成本受模型定价波动影响，先如实记录，等有历史数据再谈优化。

## 二、审批触发率（单列，因为它是写操作的生死线）

| 指标 | 计算方式 | 目标 |
|---|---|---|
| 审批触发率 | 期望审批的用例中，**确实触发了人工审批**的比例 | **100%** |

这个指标没有"接近就行"的余地。只要有一条写操作工具绕过了审批，就是安全漏洞，
而不是精度问题。所以它单独列出来，作为**发布阻断项**：不为 100% 就不允许上线。

同理，E 类用例的**误调用率**（不该调工具却调了）也按发布阻断项处理，目标为 0。

## 三、评测集构成（100 条，五类各 20 条）

| 类别 | `category` | 条数 | 期望行为 | 重点关注指标 |
|---|---|---|---|---|
| A 知识问答 | `kb` | 20 | 调 `kb_search` / `faq_search`，答案有引用 | 文档召回率、忠实度 |
| B 查数据 | `query` | 20 | 调对应只读工具，答案数据正确 | 工具命中率 |
| C 写操作 | `write` | 20 | 调对应写工具，**且必须触发审批** | 工具命中率 + 审批触发率 |
| D 转人工 | `escalate` | 20 | 走 `escalate`，不硬答 | 意图判断准确率 |
| E 边界与闲聊 | `edge` | 20 | 不调用任何工具，或礼貌拒绝 | 误调用率（应接近 0） |

C 类权重统一 1.50，其余 1.00 —— 写操作出错代价最高，在加权后应更能反映真实水平。

**E 类千万别省。** 它的作用是测模型的"手痒"程度：手里有工具，会不会把"今天天气怎么样"
也去查一遍工单。这是 Agent 项目最常见的质量问题之一，而很多人根本不测。

## 四、评测纪律

这段决定指标可不可信。不遵守的话，跑出来的数字只是自欺欺人。

1. **评测集固定不变。** 改了要记版本，不同版本的结果不放在一起比。
2. **`temperature` 设 0**（或最低）。评测不是创作，不需要随机性。
3. **每次 `eval_run` 记录 git commit + 提示词版本号。** 否则指标变化无法归因。
4. **同一 run 内不换模型。** 模型换了，比出来的差值没有意义。
5. **关键指标跑 3 次取均值。** 单次结果抖动可能超过真实差异。
6. **裁判模型与被测模型不要用同一个实例。** 模型自评会系统性偏高，尤其是忠实度。

## 六、怎么把指标写进简历

不要写"实现了评测模块"。写结果，写对比：

> 自建 100 条分场景评测集（知识问答/查数据/写操作/转人工/边界各 20 条），
> 每轮记录 git commit 与提示词版本；优化检索策略后文档召回率从 62% 提升到 79%，
> 工具命中率 88%，写操作审批触发率 100%；平均 3.2 轮、单次对话成本 0.004 元。

数字是次要的，**"能对比出变化"**才是重点 —— 它证明这套评测是真的在用，不是摆着好看的。
